# تقرير اختبار منظومة الجمعيات — تحديث 17 أكتوبر 2026

## بيئة الاختبار

- الواجهة: Angular 21 وVitest وPlaywright Chromium.
- الخادم: .NET 10 وSQL Server المحلي. اختبارات التكامل تنشئ قاعدة مؤقتة باسم `CharityQA_Integration_<GUID>` وتزيلها بعد الاختبار.
- تجربة المتصفح: Angular على `localhost:4200` متصل بخادم حقيقي وقاعدة SQL منفصلة `CharityQA_Ui_Roles_20261017` عبر توجيه الطلبات في Playwright. لا توجد ردود API مزيفة في اختبارات المتصفح.
- قاعدة التطبيق `CharityDb` تحتفظ بالأسر والتبرعات والجمعيات، وبعد طلب تنظيف الحسابات أصبحت تضم حساب Identity واحدًا فقط هو `admin`. تحققنا أن إعادة تشغيل الخادم لا تعيد الحسابات المحذوفة.

## أهم الأعطال التي ظهرت وصُلحت

1. أزيل تجاوز كلمة المرور من خدمة الدخول؛ حساب التجربة `admin/admin` له الآن كلمة مرور مجزأة فعلًا في Identity. كلمة المرور القديمة `Admin@123` تُحوَّل مرة واحدة عند تهيئة الداتا التجريبية، بشرط ألا يكون المستخدم قد غيّرها بنفسه.
2. كان التبرع العيني يسمح بالربط بمخزن جمعية أخرى أو بصنف مفقود، وكان يقبل قيمًا نقدية أو كميات صفرية/سالبة. الآن يرفض الطلب قبل الكتابة.
3. كان الصرف يقبل كمية صفرية أو سالبة، وقد يحفظ حركة بصنف غير موجود أو يزيد المخزون بكمية سالبة. الآن يرفض الطلب ويحافظ على الرصيد.
4. كان جرد المخزن يقبل رصيدًا سالبًا. صار التحقق في الخادم والواجهة.
5. كان تعديل تعريف الصنف من شاشة الدليل يصفر رصيده؛ صار تحديث التعريف يحافظ على الرصيد ما لم تُرسل كمية صراحة، والجرد يستخدم مسار `adjust-stock`.
6. كان إنشاء الأسرة يكرر فردًا واحدًا في الرد، وكان تعديل الفرد يكرر سجله؛ صلحت مزامنة أفراد الأسرة.
7. كان الحذف اللين يستطيع إعادة سجل مؤرشف بسبب `FindAsync`؛ القراءة الآن تحترم فلتر الأرشفة.
8. كان رد الإعدادات يعيد `CharityId` القادم من الطلب حتى لو عدّل الجمعية الحالية؛ الرد صار يحمل الجمعية الفعلية.
9. كانت التحليلات تسمح بتمرير `charityId` لجمعية أخرى؛ الآن تُرفض.

## البيانات والحسابات

`RepresentativeDemoData` يضيف ست أسر خيالية مفصلة، أربعة أفراد أسرة، سبعة تبرعات، وست حركات مساعدة، وثلاثة ملفات موظفين مرتبطة بثلاث جمعيات. البيانات موجودة في SQL Server وليست مخزنة في المتصفح. لكل سجل معرف ثابت؛ إعادة التهيئة تضيف المفقود فقط، وتحفظ تغييرات المستخدم والسجلات الموجودة. ملفات الموظفين ليست حسابات دخول.

| الحساب | كلمة مرور التجربة | الجمعية | الدور |
| --- | --- | --- | --- |
| `admin` | `admin` | أبواب الخير | Admin |

حُذفت الحسابات الستة القديمة من `CharityDb` داخل معاملة SQL، وبقي `admin` فقط. الأدمن ينشئ جمعية جديدة مع مستخدمها الأساسي في عملية واحدة، أو يضيف مستخدمًا أساسيًا لجمعية موجودة من شاشة «إدارة الجمعيات». لم ننشئ مستخدمين جددًا للجمعيات الثلاث الموجودة من تلقاء أنفسنا. تهيئة البيانات التجريبية في Development وTesting لا تعيد إنشاء الحسابات المحذوفة. الحسابات المنشأة تُخزن في Identity بكلمات مرور مجزأة.

بعد تعديل حساب المدير، اختُبر `/api/auth/login` على قاعدة التطبيق نفسها: `admin/admin` أعاد 200، بينما `admin/Admin@123` أعاد 403. كلمة المرور `admin` قصيرة ومعروفة، ولذلك هذا الحساب للتجربة المحلية فقط.

## التشغيل وإعادة الاختبار

من جذر المستودع:

```powershell
dotnet test backend/Charity.slnx --nologo
cd charity-app
npm test -- --watch=false
npm run build
```

اختبار المتصفح يحتاج خادم الواجهة على `4200` وخادم API بقاعدة SQL اختبار منفصلة على `5074` (أو ضبط `CHARITY_E2E_API` لعنوان الاختبار):

```powershell
cd qa/e2e
npm install
npx playwright install chromium
npm test
```

## حدود معروفة تحتاج قرار منتج

يوجد نوعان عمليان من الصلاحيات: `Admin` يفتح لوحة التحكم وتحليلات الشبكة ويضيف الجمعيات ومستخدميها الأساسيين؛ `CharityManager` يدير بيانات جمعيته فقط ولا يستطيع فتح التقارير أو إنشاء جمعية/مستخدم. لوحة التحكم تعرض ملخص الشبكة ثم تفاصيل الجمعية المرتبطة بحساب الأدمن، وتقرير BI الافتراضي يجمع الشبكة. اختبارات التكامل تؤكد عزل البيانات حتى إذا أرسل مستخدم الجمعية هيدر جمعية أخرى، ورفض 403 للتقارير والإضافة، وحفظ الجمعية ومستخدمها في معاملة واحدة.

- بطاقتا التبرعات ولوحة المعلومات تعرضان «إجمالي التبرعات النقدية» بدل «رصيد الخزينة»؛ لا توجد دورة مصروفات وتسويات محاسبية تكفي لحساب الرصيد الحقيقي.
- دور `Staff` محفوظ في Identity، لكن تفصيل صلاحيات الباحث والمخزن والمحاسب لكل إجراء لم يُطبق بعد؛ اختبارات العزل هنا على مستوى الجمعية.
- أزيلت أزرار فترات التحليلات التي لم تكن تغير التقرير؛ إضافة تصفية زمنية حقيقية تتطلب دعمها في API.
- رُفعت تبعية `System.Security.Cryptography.Pkcs` إلى النسخة المصححة `10.0.13`؛ تحققنا أن مشروع API يحل هذه النسخة ولم تعد تحذيرات `NU1902` و`NU1903` تظهر في اختبار التكامل.
- إعداد `Jwt:Key` ما زال ثابتًا في `appsettings.json` ويحتاج سرًا خاصًا بكل بيئة قبل النشر. تهيئة حسابات أولية فعلية لبيئة الإنتاج تحتاج مسارًا مستقلًا عن الداتا التجريبية.
