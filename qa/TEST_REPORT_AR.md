# تقرير اختبار منظومة الجمعيات — 16 أكتوبر 2026

## بيئة الاختبار

- الواجهة: Angular 21 وVitest وPlaywright Chromium.
- الخادم: .NET 10 وSQL Server المحلي. اختبارات التكامل تنشئ قاعدة مؤقتة باسم `CharityQA_Integration_<GUID>` وتزيلها بعد الاختبار.
- تجربة المتصفح: Angular على `localhost:4200` متصل بخادم حقيقي وقاعدة SQL منفصلة `CharityQA_Ui_20261016_b` عبر توجيه الطلبات في Playwright. لا توجد ردود API مزيفة في اختبارات المتصفح.
- شغّلنا التهيئة أيضًا على قاعدة التطبيق المحددة في `backend/Charity.API/appsettings.json`، وأكدنا دخول `researcher` ووجود الأسر الست الجديدة وتبرعات جمعيته المحفوظة.

## أهم الأعطال التي ظهرت وصُلحت

1. كان `admin/admin` يقبل الدخول رغم عدم مطابقته لكلمة المرور في Identity. الآن يقبل النظام كلمة المرور المخزنة فقط.
2. كان التبرع العيني يسمح بالربط بمخزن جمعية أخرى أو بصنف مفقود، وكان يقبل قيمًا نقدية أو كميات صفرية/سالبة. الآن يرفض الطلب قبل الكتابة.
3. كان الصرف يقبل كمية صفرية أو سالبة، وقد يحفظ حركة بصنف غير موجود أو يزيد المخزون بكمية سالبة. الآن يرفض الطلب ويحافظ على الرصيد.
4. كان جرد المخزن يقبل رصيدًا سالبًا. صار التحقق في الخادم والواجهة.
5. كان تعديل تعريف الصنف من شاشة الدليل يصفر رصيده؛ صار تحديث التعريف يحافظ على الرصيد ما لم تُرسل كمية صراحة، والجرد يستخدم مسار `adjust-stock`.
6. كان إنشاء الأسرة يكرر فردًا واحدًا في الرد، وكان تعديل الفرد يكرر سجله؛ صلحت مزامنة أفراد الأسرة.
7. كان الحذف اللين يستطيع إعادة سجل مؤرشف بسبب `FindAsync`؛ القراءة الآن تحترم فلتر الأرشفة.
8. كان رد الإعدادات يعيد `CharityId` القادم من الطلب حتى لو عدّل الجمعية الحالية؛ الرد صار يحمل الجمعية الفعلية.
9. كانت التحليلات تسمح بتمرير `charityId` لجمعية أخرى؛ الآن تُرفض.

## البيانات والحسابات

`RepresentativeDemoData` يضيف ست أسر خيالية مفصلة، أربعة أفراد أسرة، سبعة تبرعات، وست حركات مساعدة، وثلاثة ملفات موظفين مرتبطة بثلاث جمعيات. البيانات موجودة في SQL Server وليست مخزنة في المتصفح. لكل سجل معرف ثابت؛ إعادة التهيئة تضيف المفقود فقط، وتحفظ تغييرات المستخدم والسجلات الموجودة. أضيفت ثلاثة حسابات موظفين إلى الحسابات الأربعة الأصلية، وكلها مخزنة في جداول ASP.NET Core Identity بكلمات مرور مجزأة.

| الحساب | كلمة مرور التجربة | الجمعية | الدور |
| --- | --- | --- | --- |
| `admin` | `Admin@123` | أبواب الخير | Admin |
| `abwab` | `User@123` | أبواب الخير | CharityManager |
| `amal` | `Amal@123` | الأمل | CharityManager |
| `sedaka` | `Sedaka@123` | رسالة الصداقة | CharityManager |
| `researcher` | `Research@123` | أبواب الخير | Staff |
| `amalstaff` | `AmalStaff@123` | الأمل | Staff |
| `sedakastaff` | `SedakaStaff@123` | رسالة الصداقة | Staff |

هذه بيانات تجربة معلنة؛ غيّر كلمات المرور واحذف أزرار الدخول السريع قبل استخدام بيانات حقيقية أو نشر النظام. النظام لا يملك بعد شاشة إدارة المستخدمين أو دورة استعادة كلمة المرور.

## التشغيل وإعادة الاختبار

من جذر المستودع:

```powershell
dotnet test backend/Charity.slnx --nologo
cd charity-app
npm test -- --watch=false
npm run build
```

اختبار المتصفح يحتاج خادم الواجهة على `4200` وخادم API بقاعدة SQL اختبار منفصلة على `5074` (أو ضبط `CHARITY_E2E_API` لعنوان الاختبار):

```powershell
cd qa/e2e
npm install
npx playwright install chromium
npm test
```

## حدود معروفة تحتاج قرار منتج

- بطاقة «رصيد الخزينة» تحسب إجمالي التبرعات النقدية؛ لا توجد دورة مصروفات وتسويات محاسبية تكفي لحساب الرصيد الحقيقي.
- دور `Staff` محفوظ في Identity، لكن تفصيل صلاحيات الباحث والمخزن والمحاسب لكل إجراء لم يُطبق بعد؛ اختبارات العزل هنا على مستوى الجمعية.
- زر فترات التحليلات في الواجهة يعيد تحميل نفس تقرير API دون تمرير الفترة؛ يلزم ربط التصفية قبل اعتبارها ميزة مكتملة.
- بناء .NET أصدر تحذيري `NU1902` و`NU1903` عن تبعية عابرة `System.Security.Cryptography.Pkcs 9.0.11`. لم نغيّر نسخة الحزمة في هذا العمل؛ يجب مراجعة تحديث التبعية قبل النشر.
